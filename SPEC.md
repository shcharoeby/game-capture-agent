# Game Capture Agent для Heroes Tournament — Техническое задание

---
## 1. Назначение

Приложение запускается на машине игрока перед матчем. Оно автоматически:
- обнаруживает запуск игры
- начинает захват окна + аудио и стримит на MediaMTX
- пишет лог игровых событий с таймкодами
- завершает стрим при закрытии игры

Собранные данные используются для: трансляции матчей в реальном времени, архивного видео, автоматической нарезки по таймкодам.

---
## 2. Платформы

- Windows — приоритет (большинство игроков)
- macOS — поддержка обязательна
- Дистрибуция: single executable или zip с exe (без установщика, unzip & run)

## 4. Захват и стриминг

### 4.1 Видео — захват окна

| ОС | Метод |
|----|-------|
| Windows | gdigrab или ddagrab через FFmpeg — захват по window title/handle |
| macOS | avfoundation через FFmpeg — захват конкретного окна |

Захватывается только окно игры. Если окно свёрнуто — стрим шлёт последний кадр (freeze frame), не прерывается.

### 4.2 Аудио — захват звука игры

| ОС | Метод |
|----|-------|
| Windows | WASAPI loopback — захват того, что реально воспроизводится через динамики/наушники. Через FFmpeg: `-f dshow -i audio="virtual-audio-capturer"` или `-f wasapi -loopback` |
| macOS | BlackHole (виртуальное устройство) или ScreenCaptureKit (macOS 13+) |

Пользователь выбирает источник в настройках из списка доступных устройств. Захватывается только звук игры, не микрофон.

Кодек аудио: AAC, битрейт 192 кбит/с по умолчанию (настраивается).

### 4.3 Кодирование — только CPU

Кодек: libx264 (H.264 software encoding). Никаких аппаратных энкодеров.

Дефолтные параметры:

| Параметр | Значение | Комментарий |
|----------|----------|-------------|
| Разрешение | 1920×1080 | без даунскейла если исходник 1080p |
| FPS | 60 | |
| Битрейт видео | 6000 кбит/с | CBR |
| Пресет x264 | medium | баланс качество/CPU |
| Tune | film | приоритет качества картинки |
| Буфер кодека | bufsize = bitrate × 2 | допускает кратковременные пики |
| Аудио | AAC 192 кбит/с | |

Пресет medium выбран намеренно: приоритет — качество, а не минимальная задержка. При нехватке CPU можно снизить до faster через настройки.

### 4.4 Протокол передачи

Поддержать оба, выбор в настройках:

**RTMP:**
```
rtmp://<host>:1935/live/<key>
```

**SRT (предпочтительно при нестабильном соединении):**
```
srt://<host>:8890?streamid=publish:live/<key>&latency=3000
```

Буферизация: допускается накопление до 30 секунд перед отправкой.

## 5. Адаптивный контроль качества

### 5.1 Логика

Приложение непрерывно мониторит размер буфера отправки (сколько секунд видео накоплено, но ещё не отправлено на сервер).

```
Буфер < 10 сек   → штатный режим, битрейт не трогать
10 ≤ Буфер < 15  → предупреждение в UI (жёлтый)
Буфер ≥ 15 сек   → снизить битрейт на один шаг (default: -500 kbps)
Буфер ≥ 25 сек   → снизить ещё раз немедленно
Буфер ≥ 30 сек   → сбросить до минимального битрейта (default: 2000 kbps)
```

При восстановлении (буфер стабильно < 5 сек на протяжении 60 сек):
Постепенно поднимать битрейт обратно (+500 kbps каждые 30 сек) до дефолтного

### 5.2 Реализация

Смена битрейта делается через перезапуск FFmpeg subprocess с новыми параметрами. Это допустимо — небольшой шов в видео лучше, чем потеря буфера.

В UI показывать текущий активный битрейт и историю изменений в логе событий:
```json
{"abs": "...", "rel": 1234.5, "event": "bitrate_reduced", "from": 6000, "to": 5500, "reason": "buffer_15s"}
```

### 5.3 Параметры (настраиваемые)

| Параметр | Дефолт |
|----------|--------|
| Макс. буфер | 30 сек |
| Порог снижения | 15 сек |
| Мин. битрейт | 2000 кбит/с |
| Шаг снижения | 500 кбит/с |
| Шаг восстановления | 500 кбит/с |
| Пауза восстановления | 30 сек |

## 6. Обнаружение игры

- Конфигурируемый список имён процессов: `["heroes3.exe", "MMH55.exe", "HotA_launcher.exe"]`
- Polling каждые 3 секунды
- При обнаружении → ждать N секунд (конфиг, default 5с) → начать захват
- При исчезновении процесса → корректно завершить стрим (flush буфера, записать stream_end)

Дополнительно: сверять заголовок окна, чтобы не цепляться за лаунчеры.

## 7. Лог событий

### 7.1 Формат

Newline-delimited JSON (.jsonl), один объект на строку:

```jsonl
{"abs": "2025-06-15T14:23:45.123Z", "rel": 0.0,     "event": "stream_start",    "key": "09b6db3c...", "bitrate": 6000}
{"abs": "2025-06-15T14:23:50.800Z", "rel": 5.677,   "event": "game_detected",   "process": "heroes3.exe"}
{"abs": "2025-06-15T14:24:12.001Z", "rel": 26.878,  "event": "turn_start",      "data": {}}
{"abs": "2025-06-15T14:27:33.412Z", "rel": 228.289, "event": "combat_start",    "data": {}}
{"abs": "2025-06-15T14:29:01.100Z", "rel": 316.000, "event": "combat_end",      "data": {}}
{"abs": "2025-06-15T14:31:45.000Z", "rel": 480.000, "event": "turn_end",        "data": {}}
{"abs": "2025-06-15T14:35:10.200Z", "rel": 685.077, "event": "bitrate_reduced", "from": 6000, "to": 5500, "reason": "buffer_15s"}
{"abs": "2025-06-15T16:45:10.200Z", "rel": 8485.077,"event": "stream_end",      "reason": "game_closed"}
```

Поле `rel` — секунды от начала стрима = таймкод для нарезки.

Файл сохраняется в `./logs/{date}_{key}.jsonl`.

### 7.2 Детекция игровых событий

Только анализ экрана. Без чтения памяти, без API игры.

Методы по приоритету:

**а) Pixel/color detection** — самый дешёвый, polling раз в 500 мс
Проверить конкретный пиксель или среднее по региону на соответствие цвету.

**б) Template matching (OpenCV)**
Поиск картинки-шаблона (кнопка "конец хода", боевой экран) в указанном регионе. Threshold настраивается.

**в) OCR региона (Tesseract)**
Для текстовых данных (номер хода, имя игрока). Применять точечно — дороже по CPU.

Конфигурация детекторов — отдельный файл `detectors.yaml`:

```yaml
detectors:
  - id: combat_start
    method: template
    region: [0, 0, 1280, 100]      # x, y, w, h в координатах 1280x720
    template: templates/combat_bar.png
    threshold: 0.85
    cooldown_sec: 30

  - id: turn_end_button
    method: pixel
    region: [1150, 680, 100, 30]
    color: [255, 200, 50]
    tolerance: 20
    cooldown_sec: 5

  - id: turn_number
    method: ocr
    region: [600, 10, 80, 30]
    cooldown_sec: 60
```

Частота сэмплирования: 1–2 раза в секунду.

## 10. Мониторинг буфера через FFmpeg stderr

FFmpeg при `-progress pipe:2` выводит строки вида:
```
frame=3600 fps=60 q=22.0 size=  45000kB time=00:01:00.00 bitrate=6000kbps speed=1.00x
```

- `speed < 1.0` → кодирование не успевает → буфер растёт
- `speed > 1.0` → кодирование успевает → буфер дренируется

При `speed < 0.5` на протяжении 3+ секунд → триггер снижения битрейта.

## 11. Инструмент калибровки детекторов (Debug Mode)

### 11.1 Назначение

Отдельный исполняемый файл `capture-debug.exe` / `capture-debug-mac`. Запускается один раз разработчиком или администратором турнира перед написанием `detectors.yaml`. Цель — собрать сырые данные, из которых Claude вычленит визуальные сигнатуры для каждого игрового события.

**Рабочий процесс:**
1. Запустить capture-debug
2. Запустить игру, начать обычную партию
3. Когда происходит событие (начало хода, бой и т.д.) — нажать hotkey, ввести название события
4. Поиграть так 30–60 минут, покрыв все типы событий
5. Отдать папку с логами Клоду → он сматчит таймстемпы и напишет `detectors.yaml`

### 11.2 Что фиксирует дебаг-приложение

**А) Скриншоты — каждые 200 мс**
Полный скриншот окна игры. При нажатии hotkey — дополнительно серия каждые 50 мс в течение ±3 секунд вокруг события (burst mode).
Имя файла: `{unix_ms}_{seq}.png`

**Б) Пиксельная сетка — каждые 500 мс**
Значения пикселей в каждой точке сетки 20×20 по всему окну. Сохраняется как компактный JSON:
```json
{"ts": 1718450625123, "grid": [[r,g,b], [r,g,b], ...]}
```

**В) Дамп памяти процесса — каждые 1 сек**
Дифф изменившихся регионов памяти игры:
```json
{"ts": 1718450625000, "changed": [{"addr": "0x00A1B2C3", "prev": 4, "curr": 5}, ...]}
```
Реализация: `ReadProcessMemory` (Windows) / `vm_read` (macOS). Инструмент: pymem или ctypes.

**Г) Файловая активность игры — polling каждые 2 сек**
Список файлов в папке игры, которые изменились (mtime). Копировать diff в лог.

**Д) Лог оконных сообщений (Windows only)**
Перехват WM_* сообщений игрового окна через SetWindowsHookEx.

### 11.3 Пользовательский лог событий

При нажатии hotkey (default F9) — появляется мини-попап с полем ввода события.

Быстрые кнопки:
```
[F1] turn_start   [F2] turn_end
[F3] combat_start [F4] combat_end
[F5] hero_death   [F6] city_capture
[F9] ввод вручную
```

Лог пишется в `user_events.jsonl`:
```jsonl
{"abs": "2025-06-15T14:24:12.001Z", "unix_ms": 1718450652001, "event": "turn_start",   "note": ""}
{"abs": "2025-06-15T14:27:33.412Z", "unix_ms": 1718450853412, "event": "combat_start", "note": "красный атакует синего у замка"}
```

### 11.6 Что делает Клод с этими данными

Получив папку сессии, Клод:
1. Матчит таймстемпы из `user_events.jsonl` с ближайшими скриншотами
2. Визуально анализирует скриншоты ±3 сек вокруг каждого события
3. Анализирует `memory_diff.jsonl` — находит адреса, меняющиеся строго в момент событий
4. Анализирует `pixel_grid.jsonl` — находит характерные пиксели/регионы
5. Генерирует `detectors.yaml` с конкретными координатами, цветами, шаблонами
6. Вырезает из burst-скриншотов регионы → сохраняет как `templates/*.png`

### 11.7 Ограничения

- Дебаг-режим только для разработчика/администратора
- Сессия может занять 200–800 МБ на диске
- Дамп памяти работает только если игра не защищена anti-cheat
- На macOS дамп памяти требует sudo или подписи entitlements

## 12. Что НЕ входит в объём

- Запись локального видеофайла (MediaMTX пишет на сервере)
- Захват микрофона комментатора
- Авторизация на сервере (stream key = секрет)
- Автообновление приложения
- Аппаратное ускорение (намеренно исключено)
